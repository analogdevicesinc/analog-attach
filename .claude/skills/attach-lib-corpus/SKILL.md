name: attach-lib-corpus
description: attach-lib's corpus checks (yarn corpus:diff, corpus:oracle:diff, corpus:overlays:diff), the scripts/repros/ binding scripts, yarn pipeline:view and docs/pipeline.md. Use after a pipeline change, to accept baselines, or to look at how one binding or property goes through the pipeline.
---

All paths are relative to `packages/attach-lib`.

`yarn corpus:diff` (`scripts/corpus-parse.mjs`, needs `yarn build` and the `test/linux` / `test/dt-schema` links, about 40s) parses every binding of the Linux tree and compares a hash of each `ParsedBinding` with `corpus/bindings.json`; it, the repro scripts and the corpus test pass the processed schema of the Linux tree (`<linux>/Documentation/devicetree/bindings/processed-schema.json`, `PROCESSED_SCHEMA=<file>` for another, empty for none) and the baseline records its hash; `yarn test` builds it (see Test Layout), or by hand `dt-mk-schema -j -o test/linux/Documentation/devicetree/bindings/processed-schema.json test/linux/Documentation/devicetree/bindings`; after a pipeline change run it and read the changed files (the script prints a `diff -ru` command), and `yarn corpus` to accept them.

`yarn corpus:oracle:diff [filter]` (`scripts/corpus-oracle.mjs`, same trees and processed schema, which it requires; about 70s, or under a second with `--dumps`, which reads the `ParsedBinding`s `yarn corpus` left in `corpus/cache/base/` instead of parsing) checks each `ParsedBinding` against what dt-schema itself says in the processed schema and compares the disagreements with `corpus/oracle.json`, one line per case by category: `type-gap` (ours `unknown` or only `any` cells where dt-schema knows a type), `type-mismatch`, `two-types` (dt-schema gives the name several types and ours is one of them, not a disagreement), `count-mismatch` and `row-count-mismatch` (minItems/maxItems, an unset minItems being 1), `duplicate-key` and `impossible-bound` (min above max). A node is checked against every schema dt-validate holds it to: the binding's processed schema and the ones its `$ref` and `allOf` entries name, recursively (not `if` / `then` branches), and the `select: true` ones; a property's counts are the tightest of theirs (a `oneOf` / `anyOf` bounding by its loosest branch), and its type the one the nearest of them names, else the one `generated-types` gives its name. The processed schema has no descriptions or examples, and a property no named schema defines (dt-core's) is checked for type only. `diff` prints each category's count before and after and the cases that went and came, and exits 1 on any change; `node scripts/corpus-oracle.mjs list <category> [--dumps] [filter]` prints every case of one; `yarn corpus:oracle` accepts them. Run it with `corpus:diff` after a pipeline change.

`scripts/repros/` has five small scripts for looking at one binding (they read `dist/`, so `yarn build` first, and the `test/linux` / `test/dt-schema` links): `node scripts/repros/property-type.mjs <binding> <property> [--pattern <regex>]` prints the `ParsedBinding` type of a property, and `node scripts/repros/branch.mjs <binding> '<node body>' ...` encodes nodes the way the CLI does and prints the node data (`node_data_json`) and the `required_properties` left after narrowing (to see whether an `if/then` branch is taken). `node scripts/repros/populate.mjs <binding> [--dts <file>] [--parent <node>] [--json]` populates a binding for the rpi DTS (what the corpus test does for every binding) and prints each property's type, marking the unknown and open ones. `node scripts/repros/patterns.mjs <binding> [--property <name>] [--node '<node body>']` prints the patterns the `ParsedBinding` offers (property patterns with their type, child-node patterns) beside the ones of the processed schema, its own and its `allOf` entries', so a pattern the translation drops shows; with `--property`, which of each match the name, and with `--node`, the binding narrowed for that node (the schema's `if` / `then` patterns included). `node scripts/repros/stages.mjs <binding> [property] [--pattern <regex>] [--all] [--full] [--markdown]` prints what each step of the pipeline (each stage, fixup pass and fixup, then translate) did to one property, as a diff from the step before, with the step's `summary`; with no property, which properties each step changed (it reads the `ParseOptions.trace` through `scripts/pipeline-trace.mjs`). `yarn pipeline:view <binding>... [-o <file.html>]` (`scripts/pipeline-view/build.mjs`, after a `yarn build` it runs itself) writes the same for every property of the bindings as one self-contained HTML file (default `pipeline-view.html`, gitignored; no network) and opens it in the default browser: a property list, the steps that change it, each step's diff, summary and dt-schema counterpart over the schema with its changes marked (or before | after), the `ParsedBinding` entry, and an overview of every step with the properties it changed; the URL hash keeps the binding, property and step. `<binding>` is a path under `Documentation/devicetree/bindings`.

`docs/pipeline.md` explains the pipeline: an intro (`scripts/pipeline-doc/intro.md`), a diagram and a table of the steps from their `summary` / `counterpart` fields, and walkthroughs of a few properties (`stages.mjs --markdown`, listed in `scripts/pipeline-doc/build.mjs`). It is generated, by `yarn docs:pipeline`, and not committed (gitignored, like the view's HTML): generate it to read it, after changing a step, its summary or the trees.

## Overlay corpus

`yarn corpus:overlays:diff [filter]` (`corpus/overlays/corpus.mjs`; `yarn build` first) parses every Raspberry Pi overlay of a pinned `analogdevicesinc/linux` checkout (`LINUX_COMMIT`, fetched shallow and sparse on first run into `$CORPUS_CACHE`, default `~/.cache/attach-corpus`; needs network once) against that tree's `bcm2711-rpi-4-b.dts`, and compares the result with `corpus/overlays/snapshots/`; `yarn corpus:overlays` rewrites them. Per overlay it preprocesses with `cpp` (the CLI's default preprocess-command), parses with `DeviceTreeOverlay.new_from_string`, drops `__overrides__`, records `unresolved_targets` / `unresolved_references`, prints and re-parses the overlay as a workfile, records the overlay's `reg_conflicts` / `chip_select_overflows`, and validates the CLI's stand-in tree (`validation-tree.mjs`, a copy of the CLI validate's `build_validation_dts`: keep them in step) with the dtc and dt-validate on PATH (dt-schema 2026.9, its `DT_SCHEMA_VERSION`; it refuses another) against a processed schema that `dt-mk-schema -j` builds once per run. `diff` exits 1 on crashes, new errors, changed parse results or changed warnings/reg data; removed errors only print. A full run takes about 3.5 minutes with 8 jobs (`CORPUS_JOBS`), a filtered one about 30 s, mostly `dt-mk-schema`. It is not part of `yarn test`, verify or CI. What it records comes from dt-validate and the lib's overlay checks, not from the binding property types, so a property-type change (the processed schema's) does not show in it: after that change all 435 snapshots stayed identical although 75 overlays set `sound-dai`. Check such a change with `node corpus/overlays/repros/processed-types.mjs <binding> <property>`. `node corpus/overlays/repros/corpus-class.mjs '<regex>'` lists the snapshot errors of one class, and `corpus/overlays/snapshots/TRIAGE.md` has the baseline's error classes.
