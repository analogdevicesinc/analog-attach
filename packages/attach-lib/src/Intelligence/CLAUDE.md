# Intelligence

Suggestions for configuring a peripheral, organised as **layers of context**, least system-specific first:
1. *binding* (`layers/binding.ts` → `known_properties.ts:insert_known_structures`) — well-known property shapes, plus `suggest_values` for values the binding pins (`pinned_value`: the only option of a one-value enum (a `const` is one), `true` for a required flag) and otherwise every option of a single-value enum (`enum_options`, the binding's default first; a fixed-size enum array has none). Phandle/macro enums are left to the devicetree layer. It needs `PropertyContext.binding` (the node's resolved properties + required list), which consumers pass when they have the binding;
2. *devicetree* (`layers/devicetree.ts` → `query.ts:query_devicetree`, `parents.ts:suggest_parents`) — controllers, buses and phandles of the base tree; its `suggest_values` offers the tree's labelled, enabled `fixed-clock`s for `clocks` and `regulator-fixed`s for `*-supply` (with frequency/voltage). `is_gpio_property(key)` (from `query.ts`) classifies GPIO property names, and `gpio_row_bounds` sizes their rows as dt-schema's `_fixup_items_size` does (a lone `minItems`/`maxItems` fixes the count; unsized, e.g. spi-controller `cs-gpios`, is a bare phandle-array: 1..∞ rows; `maxItems: 1` keeps the flat `fixed_index`). A `*-gpios` property the devicetree layer refines carries `ResolvedProperty.gpio_rows` (`{ min_rows, max_rows? }`, from `gpio_row_bounds` on the binding's own sizing), before and after a controller is set, so a consumer knows the row count while the type is still the controller enum (which names every gpio-controller, disabled ones included). `gpio_row_cells(devicetree, controller)` gives the cells after the controller phandle from its `#gpio-cells` (`<1>` is [number], `<2>` [number, flags], `<3>` [number, number, flags]; `flags` carries `GPIO_MACROS`), undefined for an unknown controller or one without `#gpio-cells`; `refine_gpio` shapes its row from the same helper.

## Shared helpers

- **`providers.ts`** — `find_nodes(dt, predicate)` replaces the copies in `query.ts` and `parents.ts`. `node_label(node)` = `labels.at(-1)` is the one label rule. `phandle_name(located)`, `phandle_names(dt, predicate)` build `label ?? &{path}` strings. `labelled_providers(dt, predicate)` returns labelled, enabled nodes (used by the devicetree layer's suggestions).
- **`src/Devicetree/Access.ts`** — property readers (`number_property`, `string_property`, `reference_property`, `extract_first_number`, `extract_first_reference`), node predicates (`has_flag`, `has_property`, `has_compatible`, `is_enabled`), path helpers (`parent_path`, `node_name_of`), `patch_node`, and the `LocatedNode` type. `number_property`/`reference_property` enforce single-cell arrays; `extract_first_*` work on any cell array. `DeviceTree.node_at(path)` and `DeviceTree.locate(target)` use these internally.

A layer (`layers/types.ts:IntelligenceLayer`) implements any of three optional operations: `refine_properties` (schema-level; a layer may attach concrete `ResolvedProperty.suggestions`), `suggest_values` (concrete `ValueSuggestion`s — structured cell `rows`, or `strings` / a `flag` for non-cell values, serialised by consumers) and `suggest_placement`. `ValueSuggestion.slots` (plural `string[]`) names every owner of a shared chip select; `PlacementSuggestion.slot` stays singular (a placement belongs to exactly one slot). `IntelligenceStack` (`layers/stack.ts`) folds each operation over its layers in order, passing lower layers' results up; `IntelligenceStack.default()` is binding + devicetree and is what `populate_binding` / `populate_properties` apply (extra layers and a `NodePlacement` go in their optional `options`). Layers that reason about where the node sits need a `NodePlacement` (`layers/placement.ts:placement_from_overlay`). To add a layer, implement `IntelligenceLayer` and append it with `.with(...)` — consumers don't change. `query_devicetree`, `insert_known_structures` and `suggest_parents` remain exported for direct use (the CLI calls `suggest_parents` for `add`'s parent and `list parent`).

`target = <&{/path}>` in explicit fragments is normalised to `target-path` at parse time, because `dtc` can't emit fixups for `&{/path}` in a plugin.
