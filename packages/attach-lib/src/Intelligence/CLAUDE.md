# Intelligence

Suggestions for configuring a peripheral, organised as **layers of context**, least system-specific first:
1. *binding* (`layers/binding.ts` → `known_properties.ts:insert_known_structures`) — well-known property shapes, plus `suggest_values` for values the binding pins (`pinned_value`: a `const`, a one-option string/number enum, `true` for a required flag; phandle/macro enums are left to the devicetree layer). It needs `PropertyContext.binding` (the node's resolved properties + required list), which consumers pass when they have the binding;
2. *devicetree* (`layers/devicetree.ts` → `query.ts:query_devicetree`, `parents.ts:suggest_parents`) — controllers, buses and phandles of the base tree; its `suggest_values` offers the tree's labelled, enabled `fixed-clock`s for `clocks` and `regulator-fixed`s for `*-supply` (with frequency/voltage), noted as only right if actually wired to the device;
3. *board* (`board/`) — an add-on board description (HAT, cape, …): slots, chip selects, interrupt/reset/gpio lines. `parse_board_description(yaml)` is fs-free; `board_layer(board)` builds the layer. `is_gpio_property(key)` (from `query.ts`) classifies GPIO property names, and `gpio_row_bounds` sizes their rows as dt-schema's `_fixup_items_size` does (a lone `minItems`/`maxItems` fixes the count; unsized, e.g. spi-controller `cs-gpios`, is a bare phandle-array: 1..∞ rows; `maxItems: 1` keeps the flat `fixed_index`); `gpio_signal_kinds(property)` maps name tokens to `SignalKind[]` for interrupt-before-gpio ordering. `SlotInference.unwired_reg` flags a `reg` that isn't a wired chip select. `bus_node_values` emits `[0n]` placeholder rows for chip-select gaps.

The board file (schema v4) stores only wiring: buses (`type`, `pins`, `reserved_addresses`) and slots (one bus or a switch-selected list, plus signals). Chip selects live only in slot signals and apply on the slot's spi bus; the first one is the slot's primary `reg`. Everything derivable is computed in `board/derived.ts`, never stored: `bus_chip_selects` (a bus's chip-select table and `cs-gpios` order), `gpio_usage` (free GPIOs = a caller-chosen range minus this), and `exclusive_slots`/`exclusions_of` (slots sharing a connected GPIO; a multi-bus slot's chip-select conflict only holds on its spi bus). The parser rejects wiring contradictions: a `reg` mapped to two GPIOs, a signal on a bus pin, chip selects without exactly one spi bus. Only a shared chip select makes slots exclusive (both devices would answer); other shared lines (e.g. one reset wired to two Pmods) are legitimate and only add an "also wired to …" note via `shared_with`, worded by kind (a shared reset resets every device on it). A jumper that routes a chip select to another GPIO is an unconnected chip-select signal with the **same `reg`**: `bus_chip_selects` lists it under `alternatives`, `cs-gpios` keeps the default routing and notes the remap, and the parser only rejects one `reg` on two *connected* GPIOs. Onboard slots are hidden from `suggest board-slot` and never inferred for a node unless its `reg` matches. A board may name an `overlay` (path relative to the board file, never read by the lib) shipping its onboard devices; a slot's `onboard: "&label"` ties it to a node there, and `suggest_placement` skips such occupied slots. Host facts (pinmux of other overlays) and free-form advice (`notes`) are not modelled.

A layer (`layers/types.ts:IntelligenceLayer`) implements any of three optional operations: `refine_properties` (schema-level; the board layer only attaches concrete `ResolvedProperty.suggestions`, never narrows allowed values), `suggest_values` (concrete `ValueSuggestion`s — structured cell `rows`, or `strings` / a `flag` for non-cell values, serialised by consumers) and `suggest_placement`. `ValueSuggestion.slots` (plural `string[]`) names every owner of a shared chip select; `PlacementSuggestion.slot` stays singular (a placement belongs to exactly one slot). `IntelligenceStack` (`layers/stack.ts`) folds each operation over its layers in order, passing lower layers' results up; `IntelligenceStack.default()` is binding + devicetree and is what `Attach.populate_*` apply (extra layers and a `NodePlacement` go in their optional `options`). Layers that reason about wiring need a `NodePlacement` (`layers/placement.ts:placement_from_overlay`); board slot inference from it is stateless (parent bus + `reg`, `board/slots.ts`). To add a layer, implement `IntelligenceLayer` and append it with `.with(...)` — consumers don't change. `query_devicetree`, `insert_known_structures` and `suggest_parents` remain exported for direct use (the extension calls them).

Board YAML is parsed with `mapAsMap: true`, so integer-like keys keep file order and duplicate integer keys (e.g. `0x50` and `"80"` both under `reserved_addresses`) are rejected. `target = <&{/path}>` in explicit fragments is normalised to `target-path` at parse time, because `dtc` can't emit fixups for `&{/path}` in a plugin.
