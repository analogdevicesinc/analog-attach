# CLAUDE.md

## About This Package

`attach-lib` is the core, UI-free library for Device Tree Source (DTS) parsing, binding processing, and schema validation. It is consumed by the CLI (`packages/cli`, `analog-attach`), which bundles the built `dist/`. Built with Vite (dual ESM/CJS output), tested with Vitest.

`plans/` (gitignored) contains working plans for Claude sessions.

## Commands

There is no top-level test script that isolates just this package — use `cd packages/attach-lib && yarn test`.

Lint with `yarn lint` (ESLint + unicorn, config in `eslint.config.mjs`, same as the CLI).

Tests import the package by name (`from 'attach-lib'`) or from `../src`; `vitest.config.ts` aliases `attach-lib` to `src/index.ts`, so they run on the sources and need no build (the scripts below read `dist/`). Some source files also carry inline `import.meta.vitest` doctests (e.g. `src/Bindings/fixups/*.ts`, `src/Attach/Populate.ts`) picked up via `includeSource` in `vitest.config.ts` — these run alongside the `test/*.test.ts` files.

`test/BindingParserCompletion.test.ts` parses the whole Linux bindings tree and populates every result for the rpi DTS (about 45s) and is off unless `BINDING_CORPUS=1` (its IIO-only rpi populate test always runs, about 4s, so it can be run from the editor); it fails on a binding that parses in `corpus/bindings.json` but not now, and prints the failures by stage and the properties that stay `unknown` or open. Snapshots in `test/expected/` are the JSON a test compares with (`toMatchFileSnapshot` of `snapshot()` from `test/bindings.ts`: keys sorted, bigints as `"<n>n"`); `yarn test -u` rewrites them. `test/bindings.ts` also has `schema_paths`, `binding(file)` (a binding of the `test/linux` tree, from `Documentation/devicetree/bindings`) and `BINDINGS`, the bindings of the snapshot suites.

Tests assert what a caller sees, not how a stage gets there: the pipeline stages before the fixups have no tests of their own, `test/PipelineRules.test.ts` writes a small binding for each of their rules and checks what `Attach.parse` gives for it. A rule's test should fail when the rule is disabled (break the code and run it), and a test that only logs or compares a function with the ones it calls is not one. Snapshots are kept for the end results (`process_binding`'s schema, the `ParsedBinding`, the populated properties).

`yarn corpus:diff` (`scripts/corpus-parse.mjs`, needs `yarn build` and the `test/linux` / `test/dt-schema` links, about 40s) parses every binding of the Linux tree and compares a hash of each `ParsedBinding` with `corpus/bindings.json`; it, the repro scripts and the corpus test pass the processed schema of the Linux tree (`<linux>/Documentation/devicetree/bindings/processed-schema.json`, `PROCESSED_SCHEMA=<file>` for another, empty for none) and the baseline records its hash; `yarn test` builds it (see Test Layout), or by hand `../cli/bundled/linux/tools/dt-mk-schema -j -o test/linux/Documentation/devicetree/bindings/processed-schema.json test/linux/Documentation/devicetree/bindings`; after a pipeline change run it and read the changed files (the script prints a `diff -ru` command), and `yarn corpus` to accept them.

`yarn corpus:oracle:diff [filter]` (`scripts/corpus-oracle.mjs`, same trees and processed schema, which it requires; about 70s, or under a second with `--dumps`, which reads the `ParsedBinding`s `yarn corpus` left in `corpus/cache/base/` instead of parsing) checks each `ParsedBinding` against what dt-schema itself says in the processed schema and compares the disagreements with `corpus/oracle.json`, one line per case by category: `type-gap` (ours `unknown` or only `any` cells where dt-schema knows a type), `type-mismatch`, `two-types` (dt-schema gives the name several types and ours is one of them, not a disagreement), `count-mismatch` and `row-count-mismatch` (minItems/maxItems, an unset minItems being 1), `duplicate-key` and `impossible-bound` (min above max). A node is checked against every schema dt-validate holds it to: the binding's processed schema and the ones its `$ref` and `allOf` entries name, recursively (not `if` / `then` branches), and the `select: true` ones; a property's counts are the tightest of theirs (a `oneOf` / `anyOf` bounding by its loosest branch), and its type the one the nearest of them names, else the one `generated-types` gives its name. The processed schema has no descriptions or examples, and a property no named schema defines (dt-core's) is checked for type only. `diff` prints each category's count before and after and the cases that went and came, and exits 1 on any change; `node scripts/corpus-oracle.mjs list <category> [--dumps] [filter]` prints every case of one; `yarn corpus:oracle` accepts them. Run it with `corpus:diff` after a pipeline change.

`scripts/repros/` has four small scripts for looking at one binding (they read `dist/`, so `yarn build` first, and the `test/linux` / `test/dt-schema` links): `node scripts/repros/property-type.mjs <binding> <property> [--pattern <regex>]` prints the `ParsedBinding` type of a property, and `node scripts/repros/branch.mjs <binding> '<node body>' ...` encodes nodes the way the CLI does and prints the node data (`node_data_json`) and the `required_properties` left after narrowing (to see whether an `if/then` branch is taken). `node scripts/repros/populate.mjs <binding> [--dts <file>] [--parent <node>] [--json]` populates a binding for the rpi DTS (what the corpus test does for every binding) and prints each property's type, marking the unknown and open ones. `node scripts/repros/stages.mjs <binding> [property] [--pattern <regex>] [--all] [--full] [--markdown]` prints what each step of the pipeline (each stage, fixup pass and fixup, then translate) did to one property, as a diff from the step before, with the step's `summary`; with no property, which properties each step changed (it reads the `ParseOptions.trace` through `scripts/pipeline-trace.mjs`). `yarn pipeline:view <binding>... [-o <file.html>]` (`scripts/pipeline-view/build.mjs`, after a `yarn build` it runs itself) writes the same for every property of the bindings as one self-contained HTML file (default `pipeline-view.html`, gitignored; no network) and opens it in the default browser: a property list, the steps that change it, each step's diff, summary and dt-schema counterpart over the schema with its changes marked (or before | after), the `ParsedBinding` entry, and an overview of every step with the properties it changed; the URL hash keeps the binding, property and step. `<binding>` is a path under `Documentation/devicetree/bindings`.

`docs/pipeline.md` explains the pipeline: an intro (`scripts/pipeline-doc/intro.md`), a diagram and a table of the steps from their `summary` / `counterpart` fields, and walkthroughs of a few properties (`stages.mjs --markdown`, listed in `scripts/pipeline-doc/build.mjs`). It is generated, by `yarn docs:pipeline`, and not committed (gitignored, like the view's HTML): generate it to read it, after changing a step, its summary or the trees.

### Overlay corpus

`yarn corpus:overlays:diff [filter]` (`corpus/overlays/corpus.mjs`; `yarn build` first) parses every Raspberry Pi overlay of a pinned `analogdevicesinc/linux` checkout (`LINUX_COMMIT`, fetched shallow and sparse on first run into `$CORPUS_CACHE`, default `~/.cache/attach-corpus`; needs network once) against that tree's `bcm2711-rpi-4-b.dts`, and compares the result with `corpus/overlays/snapshots/`; `yarn corpus:overlays` rewrites them. Per overlay it preprocesses with `cpp` (the CLI's default preprocess-command), parses with `DeviceTreeOverlay.new_from_string`, drops `__overrides__`, records `unresolved_targets` / `unresolved_references`, prints and re-parses the overlay as a workfile, records the overlay's `reg_conflicts` / `chip_select_overflows`, and validates the CLI's stand-in tree (`validation-tree.mjs`, a copy of the CLI validate's `build_validation_dts`: keep them in step) with the CLI's bundled dtc and dt-validate (`../cli/bundled/linux/tools`, from `bundle-dt-schema.sh`) against a processed schema that `dt-mk-schema -j` builds once per run. `diff` exits 1 on crashes, new errors, changed parse results or changed warnings/reg data; removed errors only print. A full run takes about 3.5 minutes with 8 jobs (`CORPUS_JOBS`), a filtered one about 30 s, mostly `dt-mk-schema`. It is not part of `yarn test`, verify or CI. What it records comes from dt-validate and the lib's overlay checks, not from the binding property types, so a property-type change (the processed schema's) does not show in it: after that change all 435 snapshots stayed identical although 75 overlays set `sound-dai`. Check such a change with `node corpus/overlays/repros/processed-types.mjs <binding> <property>`. `node corpus/overlays/repros/corpus-class.mjs '<regex>'` lists the snapshot errors of one class, and `corpus/overlays/snapshots/TRIAGE.md` has the baseline's error classes.

## Architecture

### Core Modules

**Devicetree (`src/Devicetree/`)**
The DTS parser, printer and the ergonomic wrappers over them. `Parser/` holds the AST types (`DTS`, `DTO`, `DTNode`, `DTProperty`, `DTValue`, `Bits`), `Lexer`/`LexerInputStream`/`TokenStream` and `parse_dts` / `parse_dto` (they return `Result`; `format_parse_error` turns the error into a message with line and column; `parse_dto` rewrites an explicit fragment's `target = <&{/path}>` to `target-path = "/path"`, because `dtc` can't emit fixups for `&{/path}` in a plugin); `Printer.ts` has `print_dts`, `print_dto`, `print_property`. `DeviceTree` (`Devicetree.ts`) wraps a base tree: `new_from_string` / `new_from_file`, traversal (`as_stream`, `Stream.ts`), lookup (`node_at`, `locate`, `resolve_identifier`) and mutation (`add_node`, `remove_node`, `move_node`, `rename_node`, `set_status`, `set_property`, …). `DeviceTreeOverlay` (`DevicetreeOverlay.ts`) is an overlay over a base tree: fragments (`add_fragment`, `ensure_node`), the overlay's own and merged view (`effective_children`, `merged_tree`, `all_labels`), and `print`. `NodeBuilder` / `PropertyBuilder` build nodes and properties programmatically (value input types in `Types.ts`, type-level helpers such as `AddCallOnce` in `TypeUtilities.ts`). `Access.ts` (property readers, `LocatedNode`), `AddNode.ts`, `Labels.ts` and `UnitAddress.ts` are the helpers the CLI builds on. Everything is re-exported selectively from `src/index.ts`. `Parser/README.md` still describes the old `DtsDocument` parser and is out of date.

**Overlay checks (`src/Devicetree/RegConflicts.ts`, `src/Devicetree/References.ts`)**
`reg_conflicts(overlay)` finds sibling nodes whose `reg` clashes, and `chip_select_overflows(overlay)` the devices past their SPI controller's chip selects (`chip_selects_of`: the larger of `num-cs` and the `cs-gpios` entries, a bound only with `num-cs`, as Linux's SPI core counts them; the Intelligence `reg` suggestions use the same count). Which address a child occupies is `UnitAddress.ts`'s `occupied_address` (its `reg`, else its unit address), for `add`'s pick and the suggestions alike. `unresolved_references(overlay, under?)` lists `&label` / `&{path}` references that name no node of the base tree or the overlay, and `unresolved_targets(overlay)` lists fragments whose `target` / `target-path` doesn't exist before the fragment is applied. Labels on `__overlay__` and inside `__dormant__` fragments count, as dtc resolves them too.

**Binding processor (`src/Bindings/`)**
Turns a raw YAML binding schema into a UI-ready `ParsedBinding`. Dependencies run one way: `Bindings` (schema → `ParsedBinding`) ← `Attach` (validation and state) ← the CLI. `Bindings/Context.ts` builds a `SchemaContext` (`$RefParser` plus the ordered `(url prefix, dir)` search paths) from `SchemaPaths = { linux, dt_schema, processed_schema? }`, and `Bindings/Pipeline.ts`'s `process_binding(path, ctx)` runs the stages, returning `Result<DtBindingSchema, PipelineError>` (`{ stage, message }`):

1. `RefResolver` — `dereference` / `bundle` resolve `$ref` chains via `@apidevtools/json-schema-ref-parser`; `resolve_references` also collects the referenced schema files. The resolver tags each definition of `types.yaml` with its name under `dtType` (`DT_TYPE`), so a dereferenced property still says it was a `uint32-matrix` or a `phandle-array`; AJV knows `dtType` as an annotation
2. `PropertyResolver` — fills the `property: true` placeholders from the referenced files
3. `RedefinitionMerger` — merges the `allOf` re-definitions of a property into its root definition
4. `CanaryInserter` — injects the `CANARY` (`__canary__`) sentinel property into `allOf` `then`/`else` branches to make implicit `if/then` branches detectable by AJV
5. `JSONSchemaFixups` — patches quirks of real-world bindings before validation. One walk (`FixupWalker.ts`, modelled on dt-schema's `fixups.py`) applies node fixups to every node schema and property fixups to every property, property patterns included (`oneof_to_enum` has a walk of its own just before: the walker fixes the branches of a `oneOf` before the property, and `string_to_array` would turn each `const` into a list first); each fixup in `Bindings/fixups/` names its dt-schema counterpart (`oneof_to_enum`, `reg`, `string_to_array`, `names`, `unit_suffix`, `items_size`, `interrupts`, `remove_invalid_keys`, `node_properties`: of `fixup_node_props`, only the `pinctrl-names` and `^pinctrl-[0-9]+$` placeholders, not `status`, `phandle` or `bootph-*`). `dt_type` gives a property that doesn't `$ref` a type the one dt-schema's own schemas declare for its name (`PropertyTypes.ts` reads them from `dtschema/schemas`: `reg` is an `address`, `interrupts` a `uint32-matrix`, `-gpios` a `phandle-array`; with a `processed_schema`, the output of `dt-mk-schema -j`, the names it types for the whole Linux tree come after them, as dt-schema's `extract_types` does: `nvmem-cells`, `mux-controls`; a name typed two ways stays untyped), `matrix_rows` gives a matrix property without rows some, and `unit_cells` gives the numbers of a unit property (`-ns`, `-hz`) the bounds of their type (after `mark_integers`: a cell can be a macro). `collapse_allOf`, `mark_ifs` and `mark_integers` are ours: dt-schema keeps the `types.yaml` `$ref`s where we dereference, and still guesses a number from its `minimum` / `maximum` itself (`_is_int_schema`), as `mark_integers` does
6. `SelectedSchemas` — dt-validate checks every node against the `select: true` schemas too (dt-schema's `iio.yaml`, `clock.yaml`, `reg.yaml`, `dt-core.yaml`, the Linux tree's `gpio-consumer-common.yaml`, …): `selected_definitions(ctx)` reads their `properties` once per search paths, each dereferenced by its `/schemas/` URL (so its `types.yaml` refs keep their `dtType`) and fixed up on its own, and `merge_selected` merges them into every property a node names (`merge_definitions`, the binding's nearest, the tighter bounds kept), and their property patterns into a node's pattern of the same key: `mount-matrix` gets its 9 items, `reg` rows of 1 to 5 whole `uint32`s, `^pinctrl-[0-9]+$` is a phandle-array. They add no property, nothing to a child node of the name (`clocks`, `cpus`), nor a type alternative the binding has chosen (clock.yaml's `clock-frequency` `anyOf [uint32, uint64]`)
7. `JSONSchemaTranslate` — builds the `ParsedBinding`; a `dtType` of `phandle`, `phandle-array`, `address` or `*-matrix` makes a `matrix` (rows from the first entry of `items`, cells `any` unless the binding says more; the cells of an 8, 16 or 64-bit matrix stay numbers, as no phandle fits them, and a row keeps the `typeSize` its positions share); an integer of a `uint8` … `int64` `dtType` is a number of its range and `typeSize`. a `oneOf` of lists of `enum` / `const` entries (a `compatible`, fallbacks included) is one `list<enum>` whose options are whole values: the product of the positions of each branch, up to 512 options, else the property is not enumerated; a property dt-schema types as strings (`dtType`) that nothing else reads is a `list<string>` (the union of the enums when every branch is an open `items: {enum}` list), so a lone `compatible = "x"` stays an array for the narrowing. `patternProperties` are split by `Bindings/PatternKind.ts`: object schemas and `@` patterns become child-node rules (`pattern_properties`), the rest name properties (`property_patterns`); `false` entries are dropped, and so is a named property whose schema is `false` (forbidden, at the top level or in an applied branch)

The stages share the schema vocabulary of `Bindings/Schema.ts`: `Schema`, `PropertySchema`, `is_schema`, and `map_entries` (a pure top-down map over every entry, keeping the objects it doesn't change), `entries_of`, `value_at`, `deep_merge`. The dereferenced schema shares objects (one `types.yaml` definition under every property that names it); `PropertyResolver` copies it into a tree, which the stages after it rely on: the fixup walks change schemas in place.

A property's type is an `AttachType` (`Bindings/StructuralTypes.ts`): `flag`, `scalar` (one `Cell`), `list` (`item` one `Cell` for every value, or one per position, with optional `minItems` / `maxItems` / `typeSize` / `unique`), `matrix` (`rows` of lists), `node` (child properties) or `unknown`. A `Cell` is a `number` (optional range), an `enum` (`enum_type` says whether its options are numbers, strings, macros or phandle names; an option may be a whole list of strings, the fallback `compatible`s), a `string`, or `any` (a number, label or macro expression). A const is a one-option enum that is also the default. `is_list`, `is_open_list` (its cells `any`, or whole `uint32`s: reg.yaml's `reg`), `is_open` (an open list, or a matrix of open lists: the binding gives only the counts) and `list_cell` narrow them.

`src/Bindings/PatternExpansion.ts`'s `expand_pattern(pattern, cap = 32)` turns a binding pattern into the names it matches (`^channel@([0-9]|1[0-5])$` → channel@0 … channel@15), or into the literal stem when it is unbounded or larger than the cap (`^fan-[0-9]+$` → "fan-"). The CLI uses it for completion and `list property`.

The output is a `ParsedBinding`; AJV compiles `process_binding`'s schema only to narrow its `if/then` branches (`Attach`).

**`Attach` class (`src/Attach/`)**
`Attach.parse(bindingPath, paths: SchemaPaths, options?)` runs the pipeline and returns `Result<Attach, BindingParseError>`: an `Attach` holding the `readonly parsed_binding` and its compiled AJV schemas (`patterns` lists the child-node patterns). `Narrowing.ts` has `create_ajv()` (with the `typeSize` keyword of dt-schema's `validator.py`), `compile_targets` and `narrow(target, data)`. `narrow_binding(data)` runs a node's data (`NodeData.ts`: `node_data`, `node_data_json`: its properties as JSON, shaped by the binding's types) through the compiled schema, walks `__canary__` errors to figure out which `if/then` branches now apply (the `then` or the `else` of an `allOf` entry; a branch's `required` adds to the binding's list, binding's first) and returns the narrowed `ParsedBinding` (the other AJV errors are dropped: dt-validate checks the devicetree); `narrow_pattern_binding(pattern, data)` does the same for a child-node pattern. `Populate.ts` has the free functions `populate_binding(binding, devicetree, data, options?)` and `populate_properties`, which run the Intelligence stack over a binding (`PopulateOptions`: extra `layers`, the node's `placement`, `parent_name`, `parent_cells`; child-node patterns get the layers but not the placement, and the node's own cells as their `parent_cells`).

**Intelligence (`src/Intelligence/`)**
Suggestions for configuring a peripheral, organised as layers of context (binding → devicetree). Details — layer operations, `IntelligenceStack` — are in `src/Intelligence/CLAUDE.md`.

### Test Layout

`test/linux` and `test/dt-schema` (gitignored) are checkouts of ADI's Linux tree, at the commit `vitest.globalSetup.ts` pins, and of dt-schema, at the commit the CLI bundles (`DTSCHEMA_COMMIT` in `cli/scripts/bundle-dt-schema.sh`), which it clones again when they are at another one. Bumping the CLI's dt-schema therefore changes what the tests resolve against: run them and `yarn corpus:diff` after. The tests read their bindings from the Linux tree and resolve them against both, and against the tree's processed schema (`schema_paths` in `test/bindings.ts`, as the CLI does), which the setup builds with the CLI's bundled `dt-mk-schema` (so `cli/scripts/bundle-dt-schema.sh` must have run) when it is missing or its `processed-schema.stamp` names another Linux commit or tool `.recipe`.
## Key Conventions

- No `any` without justification.
- The `__canary__` property name (`CANARY`, exported by `CanaryInserter`) is a protocol between `CanaryInserter` and the AJV branch narrowing (`Narrowing.ts`); do not reuse it for other purposes.
- Fixups take a schema and return one; the walker clones the binding once. A new per-property fixup goes in `Bindings/fixups/` with a comment naming its dt-schema counterpart and is added to a walk of `fixup_passes` in `JSONSchemaFixups.ts`, with its `id`, a one-line `summary` and the `counterpart` (none if ours). The stages' own list is `PIPELINE_STAGES` (`Pipeline.ts`), and `PARSE_STEPS` (`Attach.ts`) adds translate and the vendor filter.
- Commit messages: short imperative present tense, prefixed with `attach-lib:` (e.g. `attach-lib: handle negative scalars in property values`).
